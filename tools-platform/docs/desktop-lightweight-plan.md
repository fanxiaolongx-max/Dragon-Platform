# 首页轻量化与桌面主窗口改造方案

> 2026-11-02 测量，基于 v1.0.524。结论：外壳继续用 Electron，力气花在“空壳 + 按需加载”上。

## 一、现状测量

### 首页一打开就加载的东西

| 类别 | 体积 | 说明 |
|---|---|---|
| 外部脚本 | 27 个，约 1.53 MB | 全部同步加载，没有 `defer` 或 `import()` |
| 内联脚本 | 3 段，约 167 KB | 主要一段 165 KB，是友链、首页渲染等主逻辑 |
| 样式表 | 11 个，约 400 KB | 另有内联 `<style>` 50 KB |
| HTML 结构 | 约 59 KB | 包括 193 个带 id 的节点、19 个内联 SVG |
| **合计** | **约 2.2 MB 未压缩 JS/CSS** | 浏览器每次都要解析、编译这些代码 |

体积最大的几个：

| 文件 | 体积 | 首屏是否需要 |
|---|---|---|
| `js/shared/navbar.js` | **631 KB / 10533 行** | 只需要导航那一小部分。里面还塞着设置弹窗（AI、租户、媒体、备份、数据导入）、告警中心、服务状态、内置工具同步等，**19 个页面都要加载它** |
| `js/home/dragon-claw.js` | 206 KB | 需要，是对话主体 |
| `css/shared.css` | 170 KB | 部分需要 |
| `js/home/workspace-panel.js` | 101 KB | 右侧工作区，可延后 |
| `js/shared/jszip.min.js` | 98 KB | **首页没有任何代码用到**，可以直接去掉 |
| `js/home/welink-threads.js` | 74 KB | 只在切到频道会话时需要 |
| `js/home/workspace.js` | 52 KB | 工具模式才需要 |
| `js/home/promo-video.js` | 44 KB | 推广小窗，可以空闲时再加载 |
| `js/home/desktop-agents.js` | 44 KB | 只有本机 Agent 功能用到 |

### 服务端
- 静态文件**没有开 gzip 压缩**（`navbar.js` 原样传 631 KB）。本机访问影响不大，局域网或远程访问时影响明显。
- 后端直接在 Electron 主进程里 `require('./backend/server.js')`（[electron-main.js:2080](../electron-main.js)）。后端有 140 个文件用到同步 IO 或 `execSync`，会阻塞主进程。
- 登录页的两张图片合计 718 KB。

### 代码里的潜在卡顿点
1. 流式输出每 26ms 把整条消息的 Markdown 全部重新渲染一次（[dragon-claw.js:927-938](../frontend/js/home/dragon-claw.js)）。
2. 多个轮询计时器常驻：告警中心、服务状态、运行日志（navbar）、Dragon Claw 每 4s 一次的 tac 轮询、desktop-agents 每秒一次的 tick、agent-discussion 每 30s 一次。
3. 页面上有 **428 个元素带 `backdrop-filter`**。

### 运行时实测（2026-11-02，本机 Mac，访问 PM2 3030，已登录，缓存命中）

测法：先在同源的轻量页面上挂好 `longtask` 和 `long-animation-frame` 监听，再把首页放进 iframe 加载。已人为注入一个 150ms 的阻塞，确认这种方法能抓到 iframe 里的长任务。

| 项目 | 结果 | 结论 |
|---|---|---|
| 首屏 | TTFB 17ms，首次绘制 92ms，DOMContentLoaded 112ms，load 约 390–530ms | 快 |
| 首屏长任务（>50ms） | **0 个** | 首屏不是卡的来源 |
| 首屏接口请求 | **一次性发出 39–46 个**，十几个在同一时刻并发 | 偏多 |
| 首屏 DOM | 5000–5900 个节点 | 偏多，但可以接受 |
| 流式渲染：带 0 / 10 / 40 轮历史（最多 4.2 万个 DOM 节点），重放 1 万字回复 | 每次平均 4.3 / 4.5 / 5.0ms，最慢 23ms，**没有长任务** | 在这台机器上**不是瓶颈** |
| 长对话滚动 | 一直贴着面板的帧率上限（约 21ms 一帧），没有超过 33ms 的帧；去掉毛玻璃后也没有可测出的差别 | 不是瓶颈 |
| 后端空闲时（每 100ms 探测一次，持续 20 秒） | 中位 3ms，p95 14ms，最慢 100ms | 正常 |
| **后端在首页加载期间** | 探测请求出现 **291ms、92ms、114ms 的卡顿**；`/api/desktop-agents/sessions` 服务端等待 267ms，**同一次加载调了两次** | **Node 事件循环被同步工作阻塞** |
| 首次进入 | `/api/ai/proactive-alert-message` 每次 1.6–1.9 秒，**被调用了两次** | 慢接口，还重复调用 |

**结论修正**：在这台 Mac 上，前端渲染和滚动都很流畅，“卡卡的”体感主要来自三点：
1. **一打开就发出四十多个请求**，后端在这段时间里被阻塞几百毫秒，所以各个面板陆续“蹦”出来。
2. 重复调用的请求和慢接口（desktop-agents/sessions、proactive-alert-message）。
3. 后端用同步 IO。放在 Electron 主进程里时，这种阻塞会直接冻住窗口。

没覆盖到的情况：Windows 和配置较低的机器、冷缓存首次打开、Chrome 同时开很多标签页、真实大模型流式输出的时候。如果你感觉卡的场景落在这几种里，需要换到那台机器上再测一次。

### 远程访问实测（https://cs.fanxiaolong.uk，经 Cloudflare，HTTP/3，2026-11-02）

| 项目 | 结果 |
|---|---|
| 静态资源 | 56 个里有 53 个命中浏览器缓存（Cloudflare 给静态文件设 4 小时缓存，自动 br 压缩），DOMContentLoaded 约 240ms，**不是瓶颈** |
| 首屏接口 | 第一波一次发出 25 个，单个耗时 100–500ms，越往后越慢（在源站排队）；后面还有 3 波，首屏数据约 1.0 秒才全部返回 |
| 推广视频 | 小窗**收起、暂停时**仍以 `preload="auto"` 下载完整的 4MB mini 视频，耗时 19 秒，和接口抢上行带宽 |

注意：用本机 HTTP/1.1 代理模拟延迟时，会碰到浏览器“每个站点最多 6 个连接”的限制，静态资源阶段会被严重夸大；但用 `http://IP:3030` 在局域网访问时，确实会受这个限制影响。

### 已完成
- 2026-11-02 `2c34ab52`：同一时刻的重复 GET 请求合并（`fetch-dedupe.js`），JSZip 改为按需加载。
- 2026-11-02：只有工具区用到的请求（统计、操作历史、友链、页面更新时间）通过 `HomeMode.whenTools()` 延后，切到工具区时立即加载，否则空闲时补上，首屏第一波从 25 个降到 21 个；推广小窗收起时不再预下载视频，每次打开首页少下载 4MB。首屏接口全部返回仍约 1.0 秒，因为剩下的都是对话区需要的请求。

- 2026-11-02 `a2277072`：首屏接口合并为 `POST /api/home/bootstrap`（进程内按原连接与请求头分发，白名单只读接口），在 `<head>` 里预取。远程首屏从约 40 个请求、4 波（约 1.0 秒）变为 1 个合并请求加 3 个零散请求，首屏数据约 0.5–0.75 秒到齐（不含 health 探测）。
- 2026-11-02：拆分 `navbar.js`，全局设置 19 个页签的渲染与操作（192 个顶层声明）移到 `navbar-settings.js`，首次打开设置时按内容版本号加载。`navbar.js` 从 631KB 降到 323KB，19 个页面都受益。`tests/navbar-settings-split.test.js` 守住拆分边界。

## 二、改造方案（按收益和风险排序）

### 第 0 步：几乎零风险，马上能见效
- 去掉首页的 `jszip.min.js`，省 98 KB。
- 后端加 `compression` 中间件，JS 和 CSS 的传输体积预计能降到 1/4 左右。
- 其余首页脚本加 `defer`，不再阻塞 HTML 解析。
- 登录页图片转成 WebP，或者降低分辨率。

### 第 1 步：给首屏请求和后端减负（实测下来对体感改善最大）
- 首屏的四十多个请求分级：只有对话核心需要的先发，其余等对应面板显示时，或者 `requestIdleCallback` 空闲时再发；能合并的合并成一个 `/api/home/bootstrap`。
- 去掉重复调用：`desktop-agents/sessions` 和 `proactive-alert-message` 在同一次加载里各被调了两次。
- 排查 `desktop-agents/sessions` 服务端那 267ms 的等待，以及首页加载期间约 290ms 的事件循环阻塞，热点路径上的同步 IO 改成异步，或者加缓存。
- 流式渲染实测不是瓶颈，顺手改成用 `requestAnimationFrame` 合并更新就够了，优先级排后。

### 第 2 步：拆 navbar.js
- 留一个 `navbar-core.js`（约 40–60 KB），只负责导航、搜索、语言切换和账号菜单。
- 设置弹窗的各个页签、告警中心、备份、数据导入、内置工具同步，拆成独立模块，**打开时再 `import()`**。
- 19 个页面都能受益。

### 第 3 步：首页改成“空壳 + 按模式加载”
- 首屏只加载：外壳（侧边栏、顶栏）、对话核心（dragon-claw 及其样式）和 api/i18n。
- 切到“工具”模式时，才加载 workspace、skills-tools、capabilities。
- 切到“频道”时，才加载 welink-threads；用到 Agent 功能时，才加载 desktop-agents 和 agent-discussion。
- 右侧工作区面板在第一次展开时加载；推广视频在 `requestIdleCallback` 空闲时再加载。
- 165 KB 的内联脚本挪到外部文件，这样能被缓存，也能拆分。
- 轮询统一改成 SSE 推送，或者至少做到“页面不可见就暂停、不在当前模式就停止”。

### 第 4 步：“发现应用”入口
- 顶部做一个“发现应用”下拉菜单，带拼音搜索（复用 `js/shared/pinyin-search.js`），分成推荐、最近使用、全部三组。
- 我的工具、内置工具和托管应用都从这里打开；左侧边栏只留高频入口。
- 工具页本身就是独立页面或 webview，打开时才加载，天然是按需加载。

### 第 5 步：桌面主窗口（Electron）
1. **先把后端移到 `utilityProcess` 子进程**，主进程只管窗口、托盘和 IPC。这一步必须排在开主窗口之前，否则后端一阻塞，整个窗口都会冻住。
2. 新增主 `BrowserWindow`：macOS 用 `titleBarStyle: 'hiddenInset'`，开 `backgroundThrottling: false`，只允许一个实例。
3. 系统浏览器访问继续保留，给局域网、手机端和 iOS App 用；启动时用主窗口还是浏览器，做成设置项。

### 可选：引入构建步骤
如果做完第 2、3 步还想继续优化，可以引入 Vite 做代码拆分和压缩，按页面逐个迁移，不需要一次重写。框架方面，原生 JS 加模块化已经够用；真要上框架，就选 Preact 或 Lit 这类轻量的。

## 三、预期效果（估算，以实测为准）

| 指标 | 现在 | 第 0–3 步之后 |
|---|---|---|
| 首屏 JS | 约 1.7 MB（含内联） | 约 300–400 KB |
| 首屏 CSS | 约 450 KB | 约 150 KB |
| 常驻轮询 | 6 个以上 | 1 个推送连接 |
| 首屏接口请求 | 39–46 个 | 10 个以内 |
| 首页加载期间的后端阻塞 | 约 290ms | 低于 50ms |

## 四、建议顺序
第 0 步 → 第 1 步 → 补测运行时数据 → 第 2 步 → 第 3 步 → 第 4 步 → 第 5 步。每一步都能单独上线、单独验证，在沙箱端口上测过后再重启 PM2。
