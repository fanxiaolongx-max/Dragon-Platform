# Python 脚本通用热更新外壳架构 (Universal Shell & Hot Updater)

## 💡 设计理念与架构

传统的 Python 打包（如直接用 PyInstaller 针对业务脚本打包为单个 EXE），存在以下痛点：
1. **体积臃肿**：每次业务逻辑改动几行代码，用户都需要重新下载 50MB~100MB 的完整绿色包或安装包；
2. **分发缓慢**：对于网络受限或企业内网用户，频繁重新下载安装成本高；
3. **版本碎片化**：用户很难即时保持最新版本。

**本方案的核心架构创新：通用外壳 + 核心逻辑动态热更新**
- **通用外壳 (`universal_shell.py` / `PR报告抽查工具.exe`)**：
  - 内置 Python 解释器与业务依赖（Pandas、OpenPyXL、xlrd）；
  - 提供轻量、现代的 GUI 操作界面；
  - 回显区只读，可选择和复制；命令通过底部「命令输入」行发送。终端工具栏提供「■ 停止」「⌫ 清屏」「↻ 重启」，清屏只清除显示内容；
  - 负责拉起交互式控制台运行核心业务脚本；
  - 提供「检查并在线热更新」功能，支持 GitHub 官方 Raw 源、国内加速镜像（ghproxy）、第三方自定义地址。
- **核心逻辑脚本 (`core_script.py`)**：
  - 纯 Python 源码（如 PR 报告抽查脚本）；
  - 启动器优先加载与自身同级目录下的 `core_script.py`；
  - 更新前校验 Python 语法和 `version.json` 的 SHA-256，备份脚本及版本信息后原子替换；下载或校验失败时保留原脚本。
  - 业务代码更新可通过「检查更新」生效；新增依赖或修改外壳时，需要下载新的完整绿色包。

## 📁 目录结构

```text
python-packager/
├── core_script.py         # 核心业务逻辑脚本（默认内置 PR 报告抽查脚本）
├── universal_shell.py     # 通用外壳启动器 GUI（带脚本更新与交互控制台运行）
├── version.json           # 当前核心脚本版本描述文件
├── updater_config.json    # 远端更新源配置（GitHub 官方源 / 加速镜像 / 自定义源）
├── requirements.txt       # Python 依赖清单
├── build_exe.py           # 本地与 CI 共用的打包入口，自动收集核心脚本依赖
├── build_exe.bat          # 本地 Windows 一键打包脚本
├── smoke_test.py          # 在临时目录验证真实菜单交互及 Excel 读写
├── tests/                 # 打包、更新与核心业务回归测试
├── run_launcher.bat       # 本地快速测试启动脚本
└── backups/               # 自动备份目录（热更新前自动备份历史版本）
```

## 🚀 GitHub Action 自动化打包

每次向 `main` 分支推送 `python-packager/**` 改动，或在 GitHub Actions 界面手动触发时：
- 工作流 `.github/workflows/package-python-exe.yml` 会在 Windows 环境自动使用 PyInstaller 编译通用外壳；
- 生成便携式压缩包 `PR报告抽查工具-Windows-x64.zip`，并作为构建工件（Artifacts）发布；
- 发布前必须通过真实 EXE 冒烟测试：从包含中文和空格的临时目录启动，验证主菜单、输入退出与 Excel 读写。测试失败则不会发布绿色包。
- `core_script.py` 的静态 `import` 会自动加入 PyInstaller 隐藏依赖；Pandas 的 Excel 引擎另外显式收集。新增第三方依赖时也应更新 `requirements.txt` 并重新发布完整绿色包。
- 平台网页中的脚本与历史版本按租户保存；「同步到仓库」负责共享发布源码，只允许在默认租户中由管理员操作。源码导出与同步需要运行环境包含完整的 `python-packager/` 目录。

## Windows 缺少模块错误（如 `No module named 'glob'`）

旧打包配置只将 `core_script.py` 作为数据文件复制，PyInstaller 无法分析运行时加载的业务依赖。新版统一打包入口会收集这些依赖，并保留标准输入输出供内置交互终端使用。

遇到该错误的旧客户端，需要下载修复后的**完整 ZIP 并解压**。可以把原来的 `data/` 复制到新目录。运行时必须保留 EXE 旁边的 `_internal/`、核心脚本和配置文件，不能只复制单个 EXE。在线更新业务脚本无法补齐旧 EXE 中缺失的 Python 模块。

本地打包运行 `build_exe.bat`；从源码验证可以运行：

```bash
python -m unittest discover -s tests -v
python smoke_test.py --source
```

## 抽查数据处理（v1.2.0）

菜单 4「抽样策略」新增重复单号处理，默认按来源类型和单号去重。相同单号的相同业务记录只计一次，来源文件列不影响去重；空单号或同号记录的状态、等级等字段有冲突时，停止抽查并提示核对源数据。可以切换成「按记录抽查」保留每条记录。去重在范围过滤及比例计算之前进行，整改单同时属于「已闭环」与「延期」时，仍可在两个范围分别抽查。

导出的「抽查配置」记录使用的处理方式，「候选统计」展示原始候选记录数、处理后候选数和抽中记录数，方便核对抽查分母。

菜单 6「自动合并」检查源文件清单与 SHA-256 内容变化，覆盖新增、删除、改名，以及保留旧修改时间的内容替换。来源记录随合并表保存在隐藏工作表中，智能导入的外部文件及同目录新增文件也会被跟踪。菜单 7 继续用于立即合并。若已有来源记录的全部源文件被移除，则停止操作并保留旧合并表，避免继续抽查旧数据；未带来源记录的手工合并表仍可直接使用。旧合并表在存在原始文件时自动重建一次，建立来源记录。
